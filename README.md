# MaiBot 好感度插件

开发者：**GPT-6.1 Sol Ultra**。发布与维护：[MoonlyCake](https://github.com/MoonlyCake)。

记录麦麦对每位用户的好感度，接管自然语言查询，并按麦麦现有人设生成简短、拟人的回复。好感度按 `platform + user_id` 保存，同一平台的群聊与私聊共享记录；范围为 **-100～100**，初始值为 **0**。

目标版本：**MaiBot 1.3.3、maibot-plugin-sdk 2.9.0、Python 3.12+**。SDK 最低版本为 **2.8.1**，使用其 `task_name` 模型任务路由。

## 安装

当前发布版本为 **v1.1.2**。从 [Release](https://github.com/MoonlyCake/maibot-affection/releases/tag/v1.1.2) 下载安装 ZIP，或直接克隆主分支。升级覆盖插件代码后重载或重启 MaiBot，原配置与好感度数据库会继续使用。

1. 下载 Release 安装 ZIP，将其中的 `affection/` 复制到 MaiBot 的 `plugins/`；如果下载 GitHub 源码 ZIP，将解压后的仓库根目录重命名为 `affection` 再复制。最终得到 `plugins/affection/plugin.py` 和 `plugins/affection/_manifest.json`。
2. 启动或重载 MaiBot，在 WebUI 插件管理中启用 **麦麦好感度**。首次加载由 Runner 根据配置模型生成 `config.toml`，可在 WebUI 调整配置。
3. 确认主程序已配置可用的 `replyer` 模型，以及麦麦昵称、人设和说话风格。

也可直接克隆仓库到 MaiBot 的插件目录：

```bash
git clone https://github.com/MoonlyCake/maibot-affection.git plugins/affection
```

插件使用标准库 SQLite，无需额外数据库服务或模型配置。

## 本地评分策略（v1.1.1 起）

基础交流改为排除式判断：明确向麦麦交流，且正文没有未解决的情绪、否定、反讽、指代等阻断信号，才给基础分。取消基础交流的 40 字限制，不再用普通聊天整句白名单。有阻断信号而组合语法未命中时记 **0**。**词表外的负面说法可能得到基础分，受冷却限制**；基础交流默认每位用户 300 秒最多结算一次，可将 `interaction_step` 设为 0 关闭。

交流收件人和情绪评价对象分别确认：群聊 @ 麦麦只能确认收件人，不能保证正文里的情绪针对麦麦。情绪规则使用词表、对象、程度词和有限语气尾模板组合（不把属格“的”统一剥除）。默认分档为 **±1、±2、±3**，每条合并后最多增减 **3**；“傻、笨”默认 -1，程度加强为 -2；“爱”默认 +2，“真的、超级、最”等加强为 +3。评分仍在本地完成，不新增模型调用或评分 Token。

空格继续分句；切分后只跨空格合并孤立称呼、程度词及依附的“的……”宾语或语气尾，不跨标点、换行或转折。褒贬不定的网络梗进入阻断词表，单字和数字梗按词法边界识别，避免误伤普通词语和数字。

独立留出集由用户或 Claude 私下保管。用户反馈：v1.1.1 中性覆盖 **95%**、情绪方向覆盖 **42%**、安全失败 **8**；v1.1.2 结构修订前中性覆盖 **95%**、安全失败 **2**，另 25 条同类新句中有 **11** 条获得基础分。本次据此加入结构规则，按用户要求直接发布；未访问私有原句，也未重跑本轮测试。

## v1.1.0 历史更新

首次加入保守的本地分句评分，用完整句式判断明确态度；未覆盖的交流记 0。该版在原 130 条人造样本上安全失败为 0，基础交流覆盖仅 **6/40（15%）**，保守漏判 **72**，是本次调整基础分和组合语法的原因。

基础交流使用新增的 `last_interaction` 冷却，明确正负情绪及插件 API 使用 `last_positive`／`last_negative`，三类冷却独立，默认间隔均为 **300 秒**。因此闲聊不会阻挡随后的感谢或其他插件上报的正向事件；明确正向情绪与正向 API 上报仍共用正向冷却。

升级时启动检查数据库，缺少 `last_interaction` 才执行 `ALTER TABLE ADD COLUMN`，保留已有分数和其他冷却。迁移同时将旧事件的 `reason` 替换为“历史事件”。新事件只保存标签，API 传入的 `reason` 不落库；事件保留 **30 天**，启动清理，之后每小时在发生事件写入时清理一次，按 `timestamp` 索引删除。去重期限同为 30 天。

## 使用与记分

私聊可直接说：

- `我的好感度多少？`
- `你喜欢我吗？`
- `你对我印象怎么样？`
- `我在你心里算什么？`
- `咱俩现在算啥关系？`

查询分成两套，读取同一份好感度：

| 模式 | 示例 | 回复方式 |
|---|---|---|
| 日常查询 | `你喜欢我吗？`、`麦麦，我在你心里算什么？`、`我的好感度多少？` | 按人设随意、拟人地聊天；问分数时自然提到分数 |
| 正式查询 | `@麦麦 查询好感度`、`@麦麦 查看我的好感度`、`/affection` | 保留人设，以严肃、认真、清晰的语气说明分数、范围和关系阶段 |

群聊默认需 **@ 麦麦**，或以麦麦昵称、别名开头。`/affection` 是正式查询的快捷命令，无需再 @。私聊可直接发送 `查询好感度`。两套使用不同的原生 Command，正则互不重叠。

查询由轻量 Hook 提取当前正文，再通过原生 `Command` 的完整句式正则接管，随后停止普通聊天流程，避免重复回复。询问分数时提示模型自然提到真实分数；询问关系时用日常感受表达。@ 位置、引用回复中的当前提问，以及 Host 已完成的语音转写都可处理；被引用、转发的历史内容以及 `他说“你喜欢我吗？”`、`如何提高好感度？`、`把我的好感度改成100` 等句子不触发查询。识别范围是代码中明确列出的中文句式，新增表达可扩展 `SCORE_PHRASES`、`RELATION_PHRASES`。

自动记分只分析用户当前正文：文本段和有效语音转写以换行连接，保留标点用于分句；引用、转发中的历史文字不参与评分。查询识别继续使用原来的规范化正文。

基础分的收件人由私聊、群聊只 @ 麦麦或句首昵称呼叫确认，不限制正文长度。其他人的 @ 或第三人引用会使基础分记 0。情绪仍需确认评价对象；群聊隐含对象的句子限于 **40 字以内**，含其他被 @ 或被引用对象时，不把裸“你”直接认作麦麦。明确指向麦麦昵称、别名的评价分句可以确认对象。`@麦麦 你看他，你说他是不是很烦` 等混合对象表达记 0。

同一对象的已确认转折以后半句为主，不同对象分别判断；未解决的态度不能被转折清除。重复的同一评价分句只算一次，各个明确评价合并后限制为 -3～3，基础分不与情绪分叠加。词表和组合语法的默认效果例如：

| 类型 | 示例 | 默认变化 |
|---|---|---|
| 无阻断信号的明确交流 | `早安`、`帮我看看这道题` | +1 基础分 |
| 感谢、轻度夸奖 | `谢谢你`、`你真棒` | +1 |
| 喜欢、亲近、较强夸奖 | `我喜欢你`、`我爱你`、`你非常棒` | +2 |
| 明确加强的喜欢 | `我真的爱你`、`我特别喜欢你` | +3 |
| 不满 | `你真烦`、`你又答错` | -1 |
| 轻度贬低 | `你好笨`、`你特别笨` | -1／-2 |
| 反感 | `我讨厌你`、`闭嘴` | -2 |
| 辱骂 | `你是垃圾`、`我恨你` | -3 |
| 不确定、未覆盖 | `你可真聪明`、`你刚才那句话让我不舒服` | 0 |
| 再次否定直接负面词组 | `不是不喜欢你`、`也不是不喜欢` | 0 |

`positive_step` 是正向最低档基数，较强／强烈档分别加 1／2；`negative_step` 是负向中档基数，轻度档减 1、强烈档加 1，各档幅度最低为 1、最高为 3。`interaction_step` 设为 0 关闭基础分，其他值同样最多给 3。旧配置中的步长不会变成每条消息固定的情绪分。

“滚、爱、好、累”等单字词只在评价语法内生效，不做任意子串匹配；“滚动、打滚、爱好、可爱的猫”等不会仅因包含单字就计情绪分。无语、服了、离谱、麻了、绷、典、急了、栓Q、对对对、呵呵、6 等网络梗阻断基础分；单字、数字梗的识别保留词法边界。

“不喜欢”“别烦我”等直接负面词组可以评分；前面有“不是、也不是、没有、并不是”等再次否定时记 0。其他未解析的否定、反讽或指代不补基础分。好感度查询、空消息、其他 `/` 命令不记分。每条消息只结算一次，基础、正向、负向分别使用自己的冷却；分数和冷却在重启后保留。

关系阶段：`-100～-41 排斥`、`-40～-11 疏远`、`-10～19 初识`、`20～49 熟悉`、`50～79 亲近`、`80～100 信任`。

两套查询分别对同一用户设置 **10 秒**冷却，日常查询后可以立即发起正式查询；同一套冷却内重复查询会静默接管。同时生成的查询回复达到上限时，也静默接管。模型或发送失败写入日志，本次查询仍已接管。

## 性能与 Token

普通消息识别、自动记分和数据库操作都在本地完成。获准回复的查询只发起一次原生 `replyer` 调用，默认输出预算 **160 Token**，提示回复为 1～2 句、80 字以内。提示仅包含缓存的人设、说话风格和当前关系信息。全局 bot 配置热更新时刷新昵称与人设缓存，插件配置热更新时刷新相关设置。

数据库位于 `ctx.paths.data_dir / "affection.sqlite3"`，通常映射到 `data/plugins/com.local.mai-affection/`。使用独立 SQLite 的原因是：分数按身份精确查询，传统数据库可以直接完成；原生 `ctx.db` 仅开放 Host 已注册的数据模型，自定义好感表适合保存在插件专属目录；embedding 和向量检索会增加模型调用与检索开销，此功能无需相似性检索。SQL 在单个工作线程执行，使用 WAL；事件去重、冷却检查和分数更新在同一事务内完成，事务中不等待模型。

`events` 保存查询和非零记分事件的去重记录，包括冷却内拒绝的事件。`reason` 仅存“基础交流”“感谢”“喜欢”“辱骂”“插件上报”等标签，不保存消息原文；合并的情绪标签用 `/` 连接。事件超过 30 天后清理，届时同一事件 ID 不再享有去重记录。分数记录长期保留。

## 消息合约与接管

本插件依赖 MaiBot 1.3.3 的 `chat.receive.after_process` 合约：该 Hook 明确允许 `modified_kwargs` 改写消息，Host 随后反序列化消息并按 `processed_plain_text` 路由原生 Command。仅命中查询时，将这一个字段设为规范化查询正文；`raw_message`、发送者与路由信息继续使用原消息。后续 Hook、会话注册和命令链看到规范化正文，这是让两套 Command 匹配当前提问的有意行为。

Hook 的 Host 序列化器明确构造 `raw_message`、`message_info.user_info.user_id`、消息段 `type/data`；文本和语音 `data` 均为字符串。插件按此合约直接读取必填字段，复用 Host 的 Hook／Command 异常隔离。成功的原生 ASR 产生 `[语音: ...]` 包装，仅完整包装会被剥除；其他预填语音文本按原文处理，关闭或失败的 ASR 占位不参与查询和记分。

所有正式与日常查询回复均通过 `send.hybrid` 发送：`reply` 段指向提问的原 `message_id`，`text` 段承载回复正文。`sync_to_maisaka_history=True` 由 Host 内部完成历史同步，所需发送能力为 `send.hybrid`。`llm.generate` 通过 `timeout_ms` 显式传入配置对应的 RPC 时限。相关固定源码：

- [HookSpec 允许改写](https://github.com/Mai-with-u/MaiBot/blob/d64a5d1ba367f316161a7dae84511d9769e77b71/src/chat/message_receive/bot.py#L88)、[消息序列化与恢复](https://github.com/Mai-with-u/MaiBot/blob/d64a5d1ba367f316161a7dae84511d9769e77b71/src/plugin_runtime/host/message_utils.py)。
- [原生 ASR 格式](https://github.com/Mai-with-u/MaiBot/blob/d64a5d1ba367f316161a7dae84511d9769e77b71/src/chat/message_receive/message.py#L419)、[混合消息发送与内部历史同步](https://github.com/Mai-with-u/MaiBot/blob/d64a5d1ba367f316161a7dae84511d9769e77b71/src/plugin_runtime/capabilities/core.py#L439)、[reply 段恢复](https://github.com/Mai-with-u/MaiBot/blob/d64a5d1ba367f316161a7dae84511d9769e77b71/src/plugin_runtime/host/message_utils.py#L276)。

## 配置默认值

| 配置项 | 默认值 | 用途 |
|---|---|---|
| `plugin.enabled` | `true` | 插件开关 |
| `plugin.config_version` | `"1.0.0"` | 配置格式标识；当前格式未变更 |
| `affection.initial_score` | `0` | 新用户初始值，-100～100 |
| `affection.automatic` | `true` | 启用本地自动记分 |
| `affection.interaction_step` | `1` | 明确中性交流的基础分，0～10，最终最多 3；0 禁用基础分 |
| `affection.positive_step` | `1` | 正向最低档基数，1～10；按强度分档，最终最多 3 |
| `affection.negative_step` | `2` | 负向中档基数，1～10；按强度分档，最终最多 3 |
| `affection.score_cooldown_seconds` | `300` | 基础、正向、负向各自的记分间隔 |
| `affection.group_requires_address` | `true` | 群聊查询需 @ 或昵称开头；评分仍需确认对象 |
| `affection.extra_names` | `[]` | 主程序昵称与别名之外的称呼 |
| `reply.cooldown_seconds` | `10` | 每用户、每套查询各自的间隔 |
| `reply.max_inflight` | `4` | 同时生成回复的上限，1～32 |
| `reply.max_tokens` | `160` | 输出 Token 上限，32～2048 |
| `reply.timeout_seconds` | `90` | 回复任务总时限与模型 RPC 时限，1～120 秒 |
| `reply.persona_max_chars` | `1200` | 缓存人设与风格的总字符预算，100～8000 |

调整 `initial_score` 只影响尚无记录的用户。关闭 `automatic` 后，其他插件仍可通过公开 API 记分。

## 其他插件调用

公开的是插件间 `API`，不会向 LLM 注册 Tool。调用名称使用清单 ID 命名空间，SDK 自动解包 Host 返回值：

这两个公开 API 面向已安装插件，不设置调用方或用户级授权。任何已安装插件都可读取指定用户的分数，并在启用时按冷却、事件去重和单次变化限制调整分数；持续调用可改变关系阶段，因此调用方属于可信插件。关闭 `plugin.enabled` 会停止调整，读取 API 仍可查询已有分数。

```python
state = await self.ctx.api.call(
    "com.local.mai-affection.get_affection",
    platform="qq",
    user_id="123456",
)
# {"score": 0, "relationship": "初识"}

result = await self.ctx.api.call(
    "com.local.mai-affection.adjust_affection",
    platform="qq",
    user_id="123456",
    stream_id="当前聊天流ID",
    event_id="来源插件:真实事件ID",
    delta=1,
    reason="完成了一次协助",
)
# {"accepted": True, "score": 1}
```

`get_affection(platform, user_id)` 返回 `score`、`relationship`，未建档用户返回初始值。`adjust_affection` 的 `event_id` 必填，`delta` 为 -10～10 的非零整数；自动评分的 ±3 限制不改变 API 的幅度。`reason` 参数保留兼容，事件仅存“插件上报”。更新遵循正向或负向冷却与分数上下限，独立于基础交流；相同 `platform + stream_id + event_id + kind="score"` 在 30 天保留期内只处理一次。重复事件或冷却内调用返回 `accepted=False` 和当前 `score`；禁用或参数错误时返回 `accepted=False` 和 `reason`。

## 后续同次回复模式

本版只有规则评分，尚未提供同次回复模式或相关配置。后续模式拟在正常回复提示中要求末尾输出固定的“对象｜态度｜强度”标签，在分段和错字处理之前解析并截除，由代码映射分数；标签缺失或解析失败记 0，不重试模型。评分指令要求态度判断不受麦麦人设影响。

第一版拟采用简单结算：开启后跳过本地情绪评分，麦麦没有回复的消息记 0，不维护待结算表。一次回复只给其目标 `message_id` 结算，其他被顺带回应的消息不计分，沿用 `kind="score"` 去重。该方案不增加评分调用，但提示与标签会增加少量 Token。

## 验证

在插件目录 `plugins/affection/` 内、Python 3.12+ 且已安装 SDK 的环境运行：

```bash
python -m unittest discover -s tests -v
```

既有规则样例分为两组：`tests/affection_samples.jsonl` 保留用户提供的 **130 条人造样本**原文、标签和顺序；`tests/scoring_cases.json` 保留 **120 条人造回归样本**，测试重点是误扣分、负面误加分和群聊对象混淆。它们已用于开发，不是独立留出验收，也不代表真实聊天准确率。新策略与旧断言的批准差异单独记录在报告中，原标签不重标。

样本按用户指定的不对称规则验收：中性交流期望 +1 时，输出 0 记为“保守漏判”，不算失败；应加却扣、应扣却加、期望不加却加、非麦麦对象被扣分均算失败。报告分别统计失败、保守漏判及强度偏差，避免把漏判称为正确识别。

结构修订前的候选提交通过 **82 项本地测试和 Ruff 检查**，包括 [四类误加分与模板边界的公开回归测试](tests/test_scoring_guards.py)。该提交在原 130 条用户样本上的结果：安全失败 **0**，中性交流覆盖 **13/40（32.5%）**，保守漏判 **69**（基础交流 27、明确情绪 42）；明确情绪方向覆盖 **30/72**，强度档位差异 **6**。其中旧标注的“爱”为 +3，新策略默认 +2，也保留为强度差异。完整结果见 [scoring_report.json](tests/scoring_report.json)。以上数字对应结构修订前，本轮按用户要求未重跑本地测试。

同一 Python 进程、相同 250 条既有样例、每版 25,000 次规则调用的本地比较：v1.1.1 平均 **7.51 μs**、P95 **13.29 μs**；v1.1.2 平均 **7.54 μs**、P95 **13.54 μs**。此比较排除 SQLite 与 RPC。

私有留出集由用户或 Claude 在仓库外保管并独立本地评估。安装 SDK 后，在插件目录运行下面的汇总入口；替换为自己的私有文件绝对路径：

```bash
python tests/evaluate_scoring.py /absolute/path/affection_holdout.jsonl --require-acceptance
```

入口只输出汇总数字，不输出正文或样例 ID，也不把留出集写入仓库。`--require-acceptance` 要求至少 100 条样例、安全失败为 0、中性覆盖率 ≥80%；任一条件不满足返回退出码 1。只将汇总结果交给实现方，避免用留出原句调整规则。

本地测试还覆盖三类记分冷却、旧库迁移、事件保留期、语音与引用边界、查询接管、持久化、并发限制和 RPC 时限传递。测试使用真实 SDK，模拟 Host RPC 边界；官方 Host 的 ManifestValidator、PluginLoader 和 ComponentRegistry 用于核验清单、加载与组件注册。部署后依次检查：

1. WebUI 中插件、两套查询 Command 与记分 Hook 正常加载，日志出现加载完成提示。
2. 私聊发送 `我的好感度多少？`，确认只有一条引用该提问、符合现有人设的短回复；10 秒内重问，确认静默。
3. 群聊分别发送无称呼及 @ 麦麦的查询，确认默认仅后者接管；随后发送 `@麦麦 查询好感度`，确认正式回复引用该提问并认真说明分数和关系。被引用、转发的历史正文和第三人称句子保留普通聊天流程。
4. 私聊发送 `早安` 后查询，确认增加 1；紧接着发送 `谢谢你`，确认再增加 1，随后 300 秒内同类消息不重复加分。不确定或混合对象的句子不加基础分。重启后确认分数与冷却保留。
5. 修改主程序人设并保存，冷却结束后再问关系，检查回复使用更新后的设定。

已按下列源码版本核对开发接口，并进行本地测试。真实 MaiBot 进程、平台适配器和在线 LLM 的完整联调尚未执行；上述部署检查用于完成该验证。
